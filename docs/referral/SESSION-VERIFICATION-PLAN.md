# Проверка сессии и условия реальных установок

Дата: 20.11.2026. Независимый аудит только локальных исходников/ранее сохранённых определений. В этом проходе не было обращений к Windows, WinSQL, production API, магазинам под учётной записью, SMS или реальным абонентам. Определения не исполнялись. Наличие исходника не доказывает текущую установленную версию.

## Вердикт

**Поддерживаемый read-only метод, достоверно подтверждающий завершённый вход и возвращающий минимальную серверную идентичность, по доступным материалам не установлен.** Это не утверждение, что такого метода нигде нет. До согласования и проверки контракта реальный verifier должен оставаться выключенным. Клиентское событие входа и совпадение переданного телефона доказательством не являются.

## Что предлагается согласовать до первого живого запроса

1. Владелец существующего API подтверждает документированный **неизменяющий данные** способ проверки уже выданной сессии. Нужны точный URL/метод/формат, гарантии различения login и pending/recovery token, срок жизни и правила отзыва. Если его нет — нужна отдельно согласованная минимальная интеграция; текущий запрет на Windows/SQL сохраняется.
2. Предлагаемый контракт (НЕ существующий endpoint): серверный `POST /referral/session/verify`, принимающий только session credential и одноразовый nonce. Возвращает `active`, immutable `subject`, канонический `phone`, `authEventId`, `authenticatedAt`, `sessionExpiresAt`, `sessionKind`; при отсутствии доказательств — отказ. Сервисные права, mTLS/подпись, replay guard и allowlist получателя согласовать отдельно.
3. Только после одобрения выполнить ограниченную проверку с выделенной тестовой учётной записью: действительная завершённая сессия; случайный/просроченный token; token pending-registration; recovery token до завершения; повтор и token после смены. Ни пароля в Linux, ни повторного `authorization`, ни вызовов `registration`/`profile`/`restore` ради lookup.
4. Один запрос, timeout, без автоматических повторов и redirect; штатная TLS-проверка. В журнал — request ID, результат классификации, длительность, HTTP-код. Не писать credential, телефон, тело ответа, URL query. Credential только в памяти на время проверки; не сохранять в реферальной БД, очереди или браузерной аналитике.
5. Если безопасный API вернёт только субъект без доказательства completed-login, считать это проверкой предъявленного credential, **не APP_LOGIN_CONFIRMED**. Для REGISTRATION_CONFIRMED дополнительно нужно независимое серверное событие завершения новой регистрации с transaction ID и состоянием до регистрации. Текущая запись t_users и текущий профиль этого не заменяют.

До этих условий **никакие существующие API-запросы не предлагается выполнять автоматически**. Для настоящего HTTP-теста оператор сначала утверждает конкретный URL/контракт и тестовую учётную запись; общий доступ к инфраструктуре не заменяет согласование.

## Передача события из приложения в Linux

После обычного успешного входа клиент может отправить кандидат на зачёт с operation ID, сохранённым invitation token (Android), заявленным каналом/версией приложения и credential по согласованному механизму. Произвольный phone/subject от клиента сервер игнорирует. Это сообщение само по себе не подтверждает событие.

Linux выполняет verifier, получает subject/phone из доверенного источника и связывает с ранее добровольно подтверждённым телефоном (iPhone) либо приглашением (Android). Привязка выполняется атомарно с уникальным зачётом subject; повторная авторизация/установка не создаёт второй результат. Конфликт нескольких приглашений требует единой серверной политики, а не произвольной замены клиентом.

Для iPhone новый вход должен сообщаться в Linux даже без локального referral token: иначе связь с подтверждённым до установки телефоном не найдётся. Отправка credential всех абонентов новому сервису требует минимизации и согласованного доверительного механизма (лучше ограниченная короткоживущая квитанция от существующего auth backend). Пока такой механизм не проверен, глобальную отправку существующих tokens не включать.

### Значение событий

| Событие | Что необходимо | Что недостаточно |
|---|---|---|
| PHONE_VERIFIED | Одноразовый challenge Linux, действительный код, TTL/attempt limits, атомарное потребление, согласие | Телефон сотрудника или введённый клиентом телефон, успешная доставка SMS |
| APP_LOGIN_CONFIRMED | Авторитетная проверка завершённой активной сессии/подписанная квитанция входа | `auth=true`, клиентский success, наличие записи/непустого пароля |
| APP_FIRST_OPEN | Первый подтверждённый сервером контакт подлинного клиента в принятой области дедупликации | Install Referrer, client platform/version или первый localStorage запуск |
| REGISTRATION_CONFIRMED | Отдельный серверный факт **нового завершения**, immutable subject и transaction ID | Первый вход в реферальную систему, совпадение телефона, старый зарегистрированный аккаунт |

Install Referrer даёт контекст установки, но значение может быть переслано произвольным HTTP-клиентом. Подтверждённый запуск требует дополнительных сигналов подлинности: [Google Play Integrity](https://developer.android.com/google/play/integrity/overview) и [Apple App Attest](https://developer.apple.com/documentation/devicecheck/validating-apps-that-connect-to-your-server), проверяемых сервером с nonce. Это отдельные не включённые интеграции. Для RuStore не предполагать наличие Google Play/Play Integrity; нужен согласованный аналогичный сигнал или честно более слабый показатель. «Первый» следует определять как первый подтверждённый контакт в реферальной системе, не обещать первый запуск за всю историю устройства/переустановок.

## Повторное использование Linux-кода

- `referral-service/integration/windows-transport.js:104–115` содержит незадействованный проектный transport для inspect/start/verify/complete/events. Эти endpoints — пакет будущего адаптера, не доказанно существующая production API. Не подключать его под видом готовой проверки сессии.
- `referral-service/ops/start-phase-a.mjs:9–19` блокирует регистрацию/SMS/удалённую конфигурацию. Новый phone-proof candidate должен включаться отдельным согласованным runtime; не включать прежний Windows poller.
- Можно повторно использовать SQLite, криптографические helpers, idempotency и UI приглашений. Старый Windows bridge/outbox не обходят отсутствие доверенного события.

## Матрица приёмки, сейчас НЕ выполненная на реальных устройствах

На каждой площадке: существующий абонент (активация, не новая регистрация), новый абонент (регистрация только с независимым событием), отказ/timeout SMS, неверный/истёкший код, повторный SMS, потеря ответа, повторный вход, переустановка, два приглашения на один телефон, смена пользователя на общем телефоне. Для Android дополнительно пропавший/невалидный referrer, неверный магазин и сеть offline; для iPhone — отсутствие приглашения в app storage при успешном сопоставлении через серверно подтверждённый телефон.

Нужны выделенные тестовые номера и согласованный отдельный SMS API (контракт/отправитель/лимиты/доступы через protected secret store), а также действительный session verifier. Без них конечный зачёт BLOCKED, даже если SDK и локальные тесты проходят. Никаких реальных данных/операций абонентов для демонстрации не использовать.
